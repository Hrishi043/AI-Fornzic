\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}
This project presents a prototype for reviewing employee activity
records for patterns associated with known insider-threat scenarios.
It processes the CERT r4.2 synthetic activity logs for logons, removable
devices, file access, email, and web activity. Event records are cleaned
and aggregated to employee-day counts. The resulting numerical features
are labelled by matching employee IDs and calendar days to the r4.2
incident windows supplied in the CERT answer file. Four models are
compared: Logistic Regression, Decision Tree, Random Forest, and
Isolation Forest. A grouped train/validation/test design keeps each
employee in only one split. Models are compared using Average Precision
and precision and recall at fixed review capacities. A count-aware
synthetic augmentation candidate for Random Forest is selected only when
its validation Average Precision exceeds the real-data baseline; the
one-percent review capacity is selected using validation F1 from a
predeclared candidate grid. On held-out real test records, the selected
Random Forest gives an F1 of 0.200 (precision 14.35\%, recall 32.87\%),
compared with 0.130 (precision 9.37\%, recall 21.45\%) for the
real-data baseline. The five-percent operating point remains as a
reference and gives higher recall but lower precision. This is a useful
signal for a research demonstration, but not evidence of wrongdoing:
unlabelled records are not confirmed benign, incident labels are
incomplete, and the tested threshold produces many records requiring
human review. A local React dashboard, backed by a FastAPI service,
scores selected activity CSV files and presents ranked review leads.
The report explains
the data pipeline, modelling, software design, evaluation, constraints,
and responsible-use safeguards.

\chapter{Introduction}
\section{Background}
Organisations record routine digital activity in access, device,
communication, file, and web logs. Those records can help an investigator
understand when an account or device behaved unusually. The volume and
variety of logs make manual review difficult, so a data-processing and
ranking tool can help prioritise records for inspection.

This project is an educational demonstration of that idea. It converts
the CERT r4.2 synthetic activity data into daily aggregates, compares
several machine-learning approaches against known incident windows, and
provides a local dashboard to explore high-priority employee-days. A
model score is a prioritisation signal only. It does not establish intent,
identity, policy violation, or guilt.

\section{Problem statement}
The prototype needs to turn a large collection of heterogeneous activity
CSV files into a compact and inspectable review queue. The analysis must
handle missing or malformed records, combine sources at a consistent
employee-day granularity, evaluate models under severe class imbalance,
and show investigators what activity contributed to a rank. Since only
known incidents are labelled, a record outside a listed incident window
must not be described as definitively normal.

\section{Objectives of the Project}
\textbf{Aim:} Build and evaluate a local, explainable-at-the-signal-level
prototype that ranks employee activity records for human review.

\textbf{Objectives}
\begin{enumerate}
  \item Inspect and clean five CERT r4.2 activity CSV sources.
  \item Aggregate activity into daily features for each user.
  \item Create a binary known-incident-window label from the answer file.
  \item Compare three supervised classifiers and one unsupervised anomaly
        detector using employee-grouped data splits.
  \item Evaluate count-aware synthetic augmentation using training data
        only, with variant selection on validation Average Precision.
  \item Evaluate ranking quality at fixed review capacities, selecting
        the reported one-percent operating point using validation F1 and
        retaining five percent as a comparison.
  \item Save model artifacts and expose a local React dashboard with a
        FastAPI service for human review of new activity records.
\end{enumerate}

\section{Scope of the Project}
The implemented feature set contains daily event counts, after-hours
counts, device connection counts, and email attachment totals when those
fields exist. It does not analyse message bodies, web URLs, or file
contents. The model target is whether an employee-day overlaps a listed
incident window in the r4.2 answer file. The prototype is not a live
monitoring system, identity-resolution system, case-management platform,
or automated disciplinary tool. The primary demonstration interface is
a local React dashboard backed by FastAPI. The earlier Streamlit
interface remains available as an alternative.

\section{Project Domain and Technology Stack}
The project falls within applied data analysis, supervised classification,
and anomaly detection. Python is used for feature preparation and model
development. pandas and NumPy support tabular processing; scikit-learn
provides the estimators, grouped splitting, and evaluation metrics; joblib
stores the fitted models; React and FastAPI provide the local interactive
demonstration \cite{reactdocs,fastapidocs}; and Streamlit remains
available as an alternative. Jupyter Notebook is used for the
reproducible analysis.

\chapter{Supporting Literature}
\section{Literature Review}
Insider-threat detection is difficult because legitimate and harmful
activity can share the same systems and workflows. A single event such
as a late login, removable-media connection, or large email attachment
is not sufficient evidence of malicious intent. This motivates combining
contextual signals and keeping a human investigator in the decision
loop. The CERT Insider Threat Test Dataset provides synthetic user
activity and scenario labels for reproducible experimentation; its
scenarios are useful for evaluating methods but cannot represent every
real organisation or establish real-world operational accuracy
\cite{cert}.

Logistic Regression is a relatively interpretable supervised baseline.
It estimates a linear decision function over the input features and can
provide a useful comparison when the relationship between engineered
features and the label is approximately additive. A Decision Tree
represents a series of feature splits and can model simple nonlinear
relationships. Random Forest averages a collection of randomized trees,
reducing the instability of a single tree and providing a flexible
tabular-data baseline \cite{breiman}.

Isolation Forest is an unsupervised anomaly-detection method. It isolates
observations through random feature and split selection; unusual points
tend to be isolated with shorter paths \cite{liu}. In this project it is
trained without using incident labels. It answers a different question
from the supervised classifiers: ``which records are unusual in this
feature space?'' Unusual does not necessarily mean incident-related.

Evaluation must reflect both the rarity of the positive class and the
intended review workflow. Accuracy can be dominated by the majority
class. Precision measures how many alerts match known positive labels;
recall measures how many known positives were retrieved. Average
Precision summarizes precision over ranked thresholds and is useful for
rare-positive ranking tasks. The scikit-learn documentation describes
these metrics and their averaging conventions \cite{sklearnmetrics}.
This project reports results at a validation-selected one-percent
employee-day capacity and retains the five-percent queue as a larger
fixed-size comparison.

\section{Literature Review Summary}
The selected methods provide complementary baselines rather than a claim
that one algorithm is universally best. Supervised algorithms can learn
patterns represented in the known incident labels; an anomaly detector
can rank deviations without those labels. For either approach, the
quality of the labels, the feature design, the data split, and the
review capacity constrain conclusions more strongly than the algorithm
name alone.

\section{Findings and Proposals}
\begin{itemize}
  \item Evaluate per-class precision and recall rather than relying on
        accuracy alone.
  \item Keep employees disjoint across model-development and test
        partitions to reduce person-specific leakage.
  \item Select a model using validation data; reserve test data for final
        reporting.
  \item Describe non-matching labels as ``not listed in known incidents''
        rather than as a verified normal class.
  \item Require independent corroboration and accountable human review
        before acting on a flag.
\end{itemize}

\section{Data preprocessing}
\subsection{Data cleaning}
Each CSV is read in chunks of 25,000 rows to limit memory use. Column
names and user IDs are normalized, timestamps are parsed, rows missing a
usable user or date are excluded, and duplicate rows within a chunk are
removed. Each retained record contributes to a calendar-day aggregate.
Where source fields are available, device ``connect'' events and email
attachment totals are separately accumulated. Missing source/day
combinations are filled with zero after source tables are combined.

The feature set intentionally excludes content, URLs, and filenames. This
reduces sensitive content processing but also limits detection to

\subsubsection{Feature groups and interpretation}
The twelve numeric fields can be read as five source-specific groups.
The event-count field measures retained row volume for that source on
one user-day. Its after-hours counterpart counts only rows in the fixed
clock interval. These paired fields distinguish total recorded volume
from the portion occurring outside the defined interval; neither field
establishes that activity was unauthorized.

The device connection count is narrower than the device event count:
it includes rows whose activity text is ``connect'' after conversion
to lowercase. The model can therefore distinguish a general device
event total from the subset marked as a connection. The email
attachment feature sums parsed attachment counts and is distinct from
the number of email rows. A single email event may contribute multiple
attachments, while an invalid attachment value contributes zero to the
sum. File and web features are event volume only; no filenames,
destinations, or contents are model inputs.

\subsubsection{Feature scale and representation}
All input values are nonnegative counts or sums, with zero used when no
matching event is present after source tables are joined. This makes the
feature matrix suitable for common tabular estimators and gives a clear
interpretation to each column. However, counts are often skewed: a small
number of user-days may have far more events than most days. Logistic
Regression standardizes the numeric input after median imputation,
whereas the tree models use count thresholds directly. The transformation
and estimator choice therefore affect how a large count changes a rank.

Because the model excludes identifiers and calendar dates, it does not
directly learn an employee's historical baseline or weekday pattern.
Two individuals with different roles can receive similar feature
vectors despite very different expectations for their work. Adding
personalized baselines may help represent context, but would require
careful protection against learning and amplifying historical bias.

\subsection{Analysis of class variables}
For each answer-file incident in dataset version 4.2, the notebook
normalizes start and end timestamps to calendar days and marks matching
user-days from the start day through the end day, inclusive. A label of
1 therefore means ``this employee-day overlaps a listed incident
window.'' A label of 0 means only that it was not marked by this
specific answer-file rule. It does not assert benign conduct. Day-level
labeling can include normal activity on the same day as an incident,
and can miss relevant activity outside its listed interval.

\subsection{Aggregation example}
Consider a user with several retained events on one calendar date. Each
row increments its source event count by one. If a timestamp falls
before 06:00 or at/after 18:00, it also increments that source's
after-hours count. A device row marked ``connect'' increments both the
device event count and the connection count. An email row with a parsed
attachment value increments the email event count by one and adds that
value to the attachment total. At the end of aggregation, these partial
source summaries are combined into a single user-day record. This
example describes the transformation rule only; it does not represent
an individual observed in the saved evaluation.

\section{Analysis of architecture and algorithms}
\subsection{Detailed study of proposed algorithms}
\textbf{Logistic Regression:} A supervised baseline with median
imputation, standard scaling, class weighting, and a maximum of 1,000
iterations. The model is fitted on the training partition and outputs
positive-class scores.

\textbf{Decision Tree:} A supervised tree with maximum depth 10,
minimum leaf size 10, and balanced class weights. These constraints
limit tree complexity compared with an unrestricted tree.

\textbf{Random Forest:} A supervised ensemble of 200 trees, minimum leaf
size 5, balanced-sub-sample class weights, and parallel fitting. It
averages tree predictions to produce a positive-class score.

\textbf{Isolation Forest:} An unsupervised anomaly detector with 200
trees, automatic contamination handling, and parallel fitting. The
negative decision function is used so larger values rank as more
unusual. The contamination setting controls the estimator's outlier
decision threshold; the project separately evaluates a validation-
selected one-percent queue and retains five percent as a reference.

\subsection{Model scoring concepts}
The four estimators produce scores through different mechanisms. The
following expressions summarize the underlying scoring ideas; they are
not a substitute for the saved estimator configuration or a claim that
the dashboard outputs are calibrated probabilities.

For Logistic Regression, the positive-class probability is modeled as
the logistic transform of a linear feature combination:
\[
\hat{p}(y=1\mid\mathbf{x}) =
\sigma\!\left(\beta_0+\sum_{j=1}^{p}\beta_jx_j\right),
\qquad
\sigma(z)=\frac{1}{1+e^{-z}}.
\]
The scaling step places numeric features on comparable ranges for
optimization, while class weighting changes the relative penalty
associated with errors on the rare positive class. Coefficients can
indicate direction within the fitted linear model, but the report does
not treat them as causal explanations.

A Decision Tree partitions the feature space through successive
threshold tests. At each node, the tree chooses a split that reduces
impurity in the child groups; a common impurity measure for binary
classification is Gini impurity,
\(G=1-\sum_{c}p_c^2\). A depth limit and minimum leaf size constrain
how specific the resulting rules can become. A single tree is easy to
trace as a sequence of conditions, but small changes in training data
can produce a different tree structure.

Random Forest fits a collection of randomized trees and aggregates
their outputs. For probability-producing trees, the ensemble score can
be represented as
\[
\hat{p}_{\mathrm{RF}}(y=1\mid\mathbf{x})
=\frac{1}{B}\sum_{b=1}^{B}
\hat{p}_{b}(y=1\mid\mathbf{x}),
\]
where \(B=200\) for the configured forest. Randomized samples and
feature choices reduce dependence on any one tree. The ensemble is
more stable than a single tree in many tabular settings, but it remains
dependent on the engineered features, labels, and sample design.

Isolation Forest repeatedly isolates observations using random feature
and split choices. Observations isolated with shorter average path
lengths are considered more anomalous. A conventional anomaly score is
often written as \(s(x,n)=2^{-E[h(x)]/c(n)}\), where \(h(x)\) is the
path length and \(c(n)\) is a normalization term for sample size.
The implementation uses the estimator's decision function with sign
reversed to align the direction with the supervised score ranks. An
unusual record in this feature space need not overlap a known incident
window, which is why anomaly scores and supervised positive-class
scores answer different questions.

After model scoring, the dashboard maps each model's values to
percentile ranks inside the current analysis. This rank transformation
supports a shared scale for presentation, but it removes the absolute
distance between two raw scores. A percentile of 0.95 means that the
record is near the high end of that run's ranked set; it does not mean
that the event has a 95 percent chance of being harmful.

\subsection{Step-by-step model workflow}
\begin{enumerate}
  \item Create numeric employee-day features and known-incident labels.
  \item Reserve one employee-grouped partition for final test evaluation.
  \item Split the remaining employees into training and validation groups.
  \item Fit all models on training records only and score validation and
        test records.
  \item Select the best model by validation Average Precision.
  \item Select review capacity by validation F1 from a coarse candidate
        grid, then compare precision and recall on held-out test employees.
        The selected rate is one percent; keep five percent as a
        larger-capacity reference.
  \item Retrain the saved dashboard bundle using the labelled table after
        evaluation. The dashboard's multi-model review scores are not the
        same thing as the single-model test comparison.
\end{enumerate}

\chapter{System Design}
\section{Model(s) Building}
The implementation is divided between the analysis notebook and the
React/FastAPI application. The notebook performs bulk preparation,
incident-window labelling, grouped evaluation, and model serialization.
The application loads the saved feature list and estimator bundle,
rebuilds employee-day features from selected CSV files, and displays
ranked review leads.

\subsection{Implementation code}
The notebook is the source of the training and evaluation workflow.
The primary dashboard uses \texttt{frontend/src/App.jsx} for the React
interface, \texttt{api.py} for its FastAPI endpoints, and
\texttt{forensic\_core.py} for CSV parsing, feature alignment,
four-model scoring, and employee ranking. The Streamlit alternative is
implemented in \texttt{app.py}. Selected source excerpts are included in
the appendix; the full source files remain in the project repository.

\subsection{Model planning and training/testing split}
The labelled employee-day records are separated by employee identifier,
not by randomly splitting individual days. This keeps one synthetic
employee's records within a single partition and reduces leakage from
repeated observations of the same employee. The training partition is
used to fit the estimators; the validation partition is used to select a
model by Average Precision; the test partition is reserved for final
comparison. Partition sizes and positive-label counts are reported in
Chapter~\ref{chap:results}.

\subsection{Training}
Logistic Regression, Decision Tree, Random Forest, and Isolation Forest
are fitted using the configured preprocessing and estimator settings
described in the system-analysis chapter. The first three use the
training labels; Isolation Forest is fitted as an unsupervised anomaly
detector without those labels. The notebook stores the model objects,
their names, and ordered feature columns in a joblib bundle for the
dashboard.

\subsection{Testing}
The held-out employee groups are scored after training. Supervised
scores use the positive-class output; Isolation Forest scores are
direction-adjusted so larger values correspond to more unusual
observations. Model selection and the test metrics are kept distinct.
The saved comparison and confusion-matrix counts are detailed in
Chapter~\ref{chap:results}; the test-set results do not validate the
dashboard's separate employee-level consensus rule.

\section{Project pipeline and output design}
The training notebook writes a model bundle containing the estimator
dictionary, feature names, and model names. The FastAPI service loads
this bundle, creates the same daily numeric feature columns from
the five input sources, fills absent columns with zero, and calculates
four model scores. Scores are converted to within-dataset percentile
ranks and averaged for a consensus employee ranking. The dashboard
marks the top five percent of users by consensus and users in the top
ten percent for at least two models as ``SUSPICIOUS''; remaining users
are marked ``REVIEW''. These are application-specific review labels,
not validated probability thresholds.

Generated CSV reports are saved under \texttt{sprint1\_output}. There is
no database in the current implementation. CSV and joblib files are
local artifacts, so file permissions, encryption, backup, and deletion
must be managed by the operator.

\subsection{Design decisions and trade-offs}
Table~\ref{tab:design-decisions} records the practical trade-offs in the
implemented prototype. These choices keep the demonstration compact and
operable on a local workstation, while identifying capabilities that
would be needed for a stronger research or operational system.

The chunk size of 25,000 rows is an implementation setting rather than
a measured optimum. A smaller chunk can reduce temporary parsing
memory while increasing loop and aggregation overhead; a larger chunk
can reduce overhead while increasing the amount of raw data held at
once. The grouped daily tables also accumulate as each chunk is
processed, so peak memory depends on the number of distinct user-day
groups as well as the chunk size. Performance claims should therefore
be based on end-to-end measurements that include parsing, aggregation,
model scoring, serialization, and output writing.

\subsection{Processing boundary and resource profile}
The dominant input in the saved run is the HTTP activity file, with
over 28 million rows. The pipeline streams this source in chunks, but
then creates grouped employee-day summaries and joins them across
sources. The number of summarized records is far smaller than the raw
event count, yet parsing and grouping still require CPU, disk access,
and intermediate memory. The notebook's model fitting adds a separate
compute cost, especially for the 200-tree ensembles. The dashboard
inference stage does not retrain the estimators; it builds features,
scores them, ranks values, and writes summaries.

No reproducible benchmark of elapsed time, peak memory, or resource
usage is currently recorded. Consequently, this report does not state
a minimum RAM size or promise a processing duration. A benchmark should
record hardware and software versions, input file sizes, row counts,
warm/cold file-cache conditions, and output dimensions. It should also
repeat runs because disk cache and background system activity can
affect wall-clock times. Such evidence would support a credible system
requirement instead of an estimate based only on the developer's
machine.

\section{Database design}
No relational database is implemented. The logical data entities are:
ActivityEvent (source row), EmployeeDay (user, day,
feature counts, target label for evaluation), ModelArtifact
(model names and feature columns), EmployeeRanking (user,
relative scores, review status), and ReviewSignal (reason and
supporting high-ranked activity day). CSV is used for tabular
interchange, and joblib serializes Python estimators. A production
version should define explicit schemas, provenance, retention controls,
and access logs before introducing persistent case data.

\subsection{Generated CSV roles}
The dashboard writes one row per employee-day to
\texttt{dashboard\_day\_scores.csv} and one row per employee to
\texttt{dashboard\_report.csv}. The day-level output supports
inspection of feature counts and model ranks over time. The employee
report supports sorting and filtering by the aggregate review status,
consensus rank, model agreement, and generated reason string. These
outputs are derived summaries and should be protected at the same level
as the source activity logs because they preserve user identifiers and
review priorities.

The in-memory state and CSV exports serve different purposes. The API
uses in-memory frames to answer detail requests for the most recent
analysis, while the CSV files persist after that process state is
replaced or the server stops. There is no mechanism to retrieve an older
analysis by identifier, compare two runs, or record the analyst who
requested a report. A later approved version could add explicit run IDs
and provenance metadata, provided that retention and access rules are
defined first.

\section{UI design}
The primary interface is a React dashboard served locally by Vite and
connected to a FastAPI service on the same computer. The landing view
includes the activity-folder picker, model names, a human-review
caution, and an expandable guide that shows how the five activity
sources become employee-day features, pass through four independent
models, and become a percentile-ranked queue. The guide explains the
distinct roles of Isolation Forest, Logistic Regression, Decision Tree,
and Random Forest. After analysis, the dashboard presents summary
counts, prioritized review cards, a searchable and filterable employee
directory, model-agreement signals, relative model ranks, and each
selected employee's highest-ranked activity days. Explanations use
aggregated counts and timing signals rather than message bodies, URLs,
or file contents. The visual design uses a dark navy sidebar, cool
neutral surfaces, and distinct restrained accents for the four model
views. The selected CSV files are sent to the local API,
staged in a temporary folder, and removed from that staging folder after
analysis; the generated dashboard summaries are saved under
\texttt{sprint1\_output}. The previous Streamlit interface remains
available as an alternative.

During analysis, the React interface displays an animated model motif,
the upload and analysis stage, and a percentage progress bar. Upload
progress comes from the browser's file-transfer events; the API reports
milestones as each activity source and model is processed. The interface
also displays an approximate remaining-time estimate extrapolated from
elapsed time and reported progress. Because progress is reported at
processing milestones and work per milestone can vary with file size,
the remaining time is indicative rather than a guaranteed completion
time. A note beside the review queue explains that model agreement counts
how many model rankings place an employee among their respective top ten
percent and that agreement is a review-prioritization signal, not a
probability or proof of misconduct.

order, with a displayed relative rank, model-agreement count, and
signal-description string. The directory provides search over the
employee ID and optional name, and a status filter. The current
interface limits the non-card directory display to 50 rows at a time;
search narrows the set. Selecting either a card or row requests the
employee detail from the API and opens a profile panel. The detail panel
compares the four within-dataset percentile ranks and lists up to twenty
activity days ordered by consensus score.

The interface is designed to help navigate the data rather than to
provide a complete investigation record. It does not retain analyst
notes, show the original raw event rows, capture a disposition, or
compare historical analysis runs. The ranked day table exposes
aggregated counts only. A reviewer still needs a separate authorized
means of examining original events and recording any conclusion.

\subsection{Accessibility and communication choices}
The analysis panel uses a live status region and a progressbar with
minimum, maximum, and current values so assistive technology can expose
the update. The folder input has an accessible label, and the error
banner has a dismiss action. Color is paired with text labels in the
review status and model names. These source-level design choices are
useful but do not amount to a completed accessibility audit; keyboard
navigation, screen-reader behavior, zoom, contrast, and responsive
layout should be reviewed in a documented acceptance test.

\section{Model planning and evaluation protocol}
The saved evaluation artifact records ranking and fixed-capacity
metrics. Average Precision selects the model. A review rate is selected
by validation F1 for that model from the candidate capacities 1\%, 2\%,
3\%, 5\%, 7.5\%, 10\%, 15\%, and 20\%; test data is not used to choose
the rate. Test metrics are reported after the model and operating
capacity are fixed. The saved split groups records by user and contains
198,259 training
rows with 815 positive labels, 66,075 validation rows with 260 positive
labels, and 66,118 test rows with 289 positive labels. The three user
sets are disjoint.

The Random Forest augmentation creates count-perturbed variants of
positive training employee-days using source-consistent Poisson and
binomial resampling. It creates one synthetic row per positive training
row (815 rows for the selected split). Synthetic rows are used only in
model fitting; validation and test data remain real and unchanged. For
each partition, scores are sorted to select the chosen proportion. This
is a ranking-based operating point, not a fixed score threshold.
The selected one-percent test queue contains 662 employee-days; the
five-percent comparison queue contains 3,306. Metrics are rounded in
the tables, so counts from the confusion matrices are authoritative.

\section{Evaluation metrics}
\textbf{Precision at 5\%} is the fraction of the fixed-size top-ranked
queue matching known positive labels. \textbf{Recall at 5\%} is the
fraction of all known positive test employee-days found in that queue.
\textbf{Average Precision (AP)} measures ranking performance across
possible score thresholds. \textbf{F1} combines positive-class precision
and recall at the selected queue rule. \textbf{Accuracy} is the fraction
of all test employee-days correctly classified at that same rule. Since
only 289 of 66,118 test records are labelled positive (0.437\%), accuracy
and weighted averages can look strong even when positive-class
precision is low. Macro average gives equal weight to class-level scores
but should not replace inspection of each class.

For a selected queue size \(k\), let \(Q_k\) be the set of the \(k\)
highest-scored test employee-days and let \(P\) be the set of all
employee-days labelled as overlapping a known incident window. The
reported capacity metrics are:
\[
\operatorname{Precision@}k = \frac{|Q_k \cap P|}{k},
\qquad
\operatorname{Recall@}k = \frac{|Q_k \cap P|}{|P|}.
\]
For the capacity-reference results, \(k=\lceil 0.05N\rceil\). The
validation-selected operating point instead uses \(k=\lceil 0.01N\rceil\).
These definitions make the review-capacity assumption explicit:
increasing \(k\) increases the number of records presented for review
and can change both precision and recall. Both rates are recalculated
within each partition and should not be mistaken for transferable
probability thresholds.

For the dashboard, let \(r_{u,d,m}\) be model \(m\)'s percentile rank
for user \(u\) on day \(d\). The interface averages the four model
percentile ranks for each employee-day and then uses that employee's
maximum daily consensus value for its employee ranking:
\[
c_{u,d} = \frac{1}{4}\sum_{m=1}^{4} r_{u,d,m},
\qquad
C_u = \max_d c_{u,d}.
\]
This is an application ranking rule, not a calibrated probability and
not the model-selection rule used in the offline evaluation. The
dashboard also uses a top-five-percent consensus cutoff and a
two-of-four model-agreement condition for its ``SUSPICIOUS'' display
status; those employee-level rules have not been evaluated by the
employee-day test metrics in this report.

\section{Discussion}
The model comparison illustrates that unsupervised anomaly detection
does not necessarily rank known incident examples well: Isolation Forest
has test recall 20.8\% and precision 1.8\% at the same queue size. The
supervised Random Forest catches more known positives in the saved test
partition after training-only synthetic augmentation. Its 14.4\%
precision still means most queued records do not match a known incident
label. The Decision Tree has test AP 0.104, below augmented Random
Forest's 0.158, and its validation AP is lower. This difference emphasizes why
validation-based selection and a one-time test evaluation should be
kept separate.

The experiment evaluates employee-days, while the dashboard ultimately
aggregates scores to rank employees. Employee-level review performance
is not established by the employee-day table. The dashboard also uses
four-model agreement and consensus ranks; those rules are not evaluated
by the reported classification metrics. Additional employee-level and
temporal validation is necessary before making claims about dashboard
effectiveness.

\subsection{Interpretation of the selected operating point}
The selected one-percent operating point is best understood as a queue
budget for a particular evaluation split. It does not mean that the
system identifies one percent of employees as risky, and it does not
mean that a score is a one-percent probability. The ranked unit in the
offline experiment is an employee-day. If an analyst can inspect only a
fixed number of employee-days, the top-ranked records define the
candidate queue; if the practical unit is an employee, aggregation and
capacity must be defined separately.

The 95 matching positive records in the test queue are useful evidence
that the selected model retrieves some known incident-window days. The
194 known positives outside the queue demonstrate that a narrow review
budget misses many labelled examples. The 567 unmatched records inside
the queue cannot be classified as either confirmed false alarms or
confirmed benign activity because the labels are incomplete. Operational
review would need a disposition process that can distinguish a data
quality issue, expected work, an unresolved lead, and a corroborated
incident without converting a model score directly into an outcome.

\subsection{Error analysis priorities}
The aggregate metrics do not show why a particular test record was
ranked highly or why another positive record was missed. A useful next
analysis would inspect a stratified sample of true-positive,
unmatched-high-score, and missed-positive records. Each record would be
reviewed against the original event sequence and its answer-file
incident interval. The review should check whether the score was driven
by event volume, unusual timing, device activity, attachment counts, or
interactions among several features. Since no event-level explanation
or independent analyst adjudication was saved for this experiment, the
current report does not claim to have completed this error analysis.

Error analysis should also distinguish modeling error from measurement
error. A malformed timestamp or missing user identifier can remove
records before modelling. A duplicate may inflate an aggregate. A
day-level label can assign the same target to all activity on a day,
even where only a small subset of the events relates to the incident.
Finally, role and schedule differences can change expected activity
volume. These issues require data and process review in addition to
model tuning.

\subsection{Threats to validity}
\textbf{Construct validity:} the target is an answer-file window match,
not a direct measurement of intent or policy violation. The features
are coarse daily counts and omit content and sequence.

\textbf{Internal validity:} employee-grouped splitting limits direct
person overlap, but data cleaning, duplicate handling, and the synthetic
augmentation design can still affect the result. Only one recorded
split is summarized here, so sampling variability is not estimated.

\textbf{External validity:} CERT r4.2 is synthetic, and the experiment
does not establish performance on a live organization's systems,
workforce, logging practices, or policies. Operational data may have
different base rates and feature distributions.

\textbf{Conclusion validity:} test metrics are estimates based on 289
known positive days and a single held-out group partition. Differences
between models should not be interpreted as stable population-wide
effects without repeated splits or confidence intervals. Average
Precision and capacity metrics summarize ranking, but they do not
capture investigation time, analyst disagreement, or the consequences
of an incorrect escalation.

\subsection{Metric example}
At the selected test capacity, the queue contains 662 employee-days.
The 95 known positive days yield a precision of
\(95/662 \approx 0.144\). There are 289 known positive days in the full
test set, so recall is \(95/289 \approx 0.329\). The F1 value is the
harmonic mean of these two quantities:
\[
F_1 = 2\,\frac{\text{precision}\times\text{recall}}
{\text{precision}+\text{recall}} \approx 0.200.
\]
This calculation makes the denominator explicit. It also shows why
precision and recall should accompany a single summary score: the same
F1 can arise from different review burdens and retrieval rates.

\subsection{Analyst workflow}
\begin{enumerate}
  \item Start the FastAPI service and React development server in
        separate terminals.
  \item Confirm that the saved four-model bundle is present and contains
        all four expected estimator names and the ordered feature list.
  \item Select the folder containing the five required CSV files with
        the browser's folder picker. The browser passes those files to
        the API over the local interface.
  \item Start analysis. The API validates required files,
        parses the usable columns in 25,000-row chunks, and aggregates
        the records to employee-days. The React interface shows upload
        progress, analysis milestones, and an approximate remaining time.
  \item Review the ranked list, the relative model ranks, the model
        agreement count, and the listed activity signals. A display
        status is a review priority, not a finding of misconduct.
  \item Select an employee to inspect that employee's highest-ranked
        activity days and the associated feature counts.
  \item Retrieve the two generated CSV files from
        \texttt{sprint1\_output} and handle them under the same access
        and retention rules as the source logs.
\end{enumerate}

If required files are missing, the API reports an error and does not
proceed with scoring. The React client uses a browser folder picker and
the API is configured for local development origins on port 5173. The
Streamlit alternative uses an AppleScript folder picker and requires
macOS. No analyst-authentication step or explicit confirmation of data
authorization is implemented.

\section{Deployment limitations}
This is a local proof of concept. It has no login, role-based access,
network service controls, encrypted database, audit log, scheduled
ingestion, model registry, monitoring, or incident workflow. The joblib
file must be treated as trusted executable model data and should not be
loaded from untrusted sources. Input logs and outputs may contain
sensitive identifiers and must remain access-controlled. A public or
production deployment is outside the verified scope.

\chapter{Conclusions}
\section{Learning Outcomes}
This project provided practical experience with a complete tabular
machine-learning workflow: data inspection, chunked CSV processing,
feature aggregation, label construction, grouped model evaluation,
class-imbalance-aware metrics, model serialization, a React/Vite client,
a FastAPI service, and local dashboard development. It also highlights
the importance of distinguishing a
known-positive label from an unverified negative, separating validation
from test data, and communicating uncertainty in an investigation
support tool.

\section{Technical Skills Acquired}
The implementation applies Python, pandas, NumPy, scikit-learn,
Jupyter Notebook, joblib, FastAPI, React, Vite, Streamlit, Git, and
CSV-based data interchange.
It uses Logistic Regression, Decision Tree, Random Forest, and Isolation
Forest; grouped train/validation/test splits; Average Precision;
precision, recall, and F1; and confusion-matrix analysis.

\section{Analytical and Professional Learning}
The project demonstrates that a high overall accuracy is not sufficient
for a rare-event use case. Review capacity, false-alert burden, incomplete
labels, and the unit of evaluation must be considered together. The
dashboard must be used as a human-review aid, with original records and
independent context checked before drawing conclusions. These are
project-derived learning points; this report does not make claims about
unverified internship activities or personal performance.

\section{Summary of the Project}
This project demonstrates a local pipeline from activity logs to
employee-day features, model evaluation, and a React/FastAPI review
dashboard. The validation-selected Random Forest's one-percent test
queue retrieves 95 of 289 known positives. These results rank synthetic
records for review; incomplete labels and low precision mean they do not
prove harmful behaviour or validate the dashboard's employee-level
status. Any operational use requires authorization, corroborating
evidence, and accountable human review.

        sequences, and contextual deviations, subject to privacy and
        authorization review.
  \item Perform false-alert case review and error analysis, while
        treating unmatched labels as unknown rather than automatically
        normal.
  \item Add automated tests for malformed input, chunk-boundary
        duplicates, missing source columns, output schemas, and model
        feature alignment.
  \item Add authenticated access, audit trails, secure storage,
        retention/deletion controls, model versioning, and documented
        analyst procedures before wider deployment.
\end{enumerate}

\subsection{Stage 1: data quality and schema contracts}
The current parser is intentionally permissive for malformed timestamps
and optional columns. A more auditable pipeline should produce a
per-file summary with the input row count, retained row count, invalid
timestamp count, missing-user count, duplicate count, and accepted
feature columns. The output should also record the parser version and
input file identity using a controlled checksum. This would help an
analyst distinguish a quiet employee-day from a day for which the input
was incomplete. Schema checks should fail clearly when a required field
is renamed or has an incompatible type, rather than allowing a partial
analysis to appear complete.

The aggregation process should have a documented duplicate policy.
Global deduplication can require extra storage or an external sort for
large files, so the chosen method should be benchmarked and described.
Feature reconciliation should compare source totals with aggregate
totals and explain any differences caused by rejected rows, optional
fields, or day alignment. These checks provide a stronger foundation
than model tuning because a model cannot recover events that were
incorrectly dropped or counted.

\subsection{Stage 2: evaluation across groups and time}
Repeated grouped splits would show how much the reported metrics depend
on which employees happen to be held out. Confidence intervals or
quantiles across the repeated runs can describe uncertainty without
pretending that one split is definitive. A time-forward evaluation
should also train on earlier periods and evaluate on later periods; this
would test a deployment question that the current employee grouping
does not answer. Where possible, both constraints should be combined so
that employee overlap and temporal leakage are examined explicitly.

The positive label definition should be reviewed alongside the
evaluation design. Incident windows can cover days containing mixed
routine and incident-related activity. Alternative label windows or
event-level labels could be studied as sensitivity analyses, provided
their definitions are set before interpreting test results. The results
should be reported separately for each label rule rather than selecting
the rule that produces the most favorable score.

\subsection{Stage 3: analyst workload and review outcome}
The queue-rate grid in the experiment gives a technical comparison,
but a real review capacity depends on the time required to inspect a
lead and the availability of trained reviewers. A future study could
record time-to-review, disposition categories, requests for additional
context, and inter-reviewer agreement. These process measures would
help determine whether a ranked queue is useful in practice. They must
be collected under an approved research and data-governance process,
with clear limits on who may see employee-level information.

\subsection{Stage 4: monitoring and change management}
If any later system is approved for continued use, each analysis should
be associated with a versioned feature definition, model artifact,
input period, and documented configuration. Changes in logging systems,
work schedules, or organizational roles can shift feature distributions
and ranking behavior. Monitoring should therefore look for changes in
data completeness, feature ranges, queue volume, and adjudicated review
outcomes. A model update should undergo the same validation and approval
process as the original version, with rollback available if quality or
governance criteria are not met.

\section{Glossary of Project Terms}
\begin{description}
  \item[Activity event] One retained row from a logon, device, file,
        email, or HTTP source after the applicable parsing and cleaning
        rules have been applied.
  \item[Employee-day] The analysis unit formed by combining all
        retained activity for one user identifier on one calendar day.
  \item[Incident window] The inclusive start and end dates associated
        with a user and scenario in the CERT answer file.
  \item[Known-window label] The binary target used in this experiment;
        a value of one indicates that the employee-day overlaps a listed
        incident window. A zero means only that the rule did not mark it.
  \item[Unlabelled record] A record without a positive answer-file
        match. It is not assumed to represent confirmed benign activity.
  \item[Feature] A numeric value derived from activity, such as a daily
        event count, after-hours count, device connection count, or
        attachment total.
  \item[Grouped split] A data partition that keeps every row for one
        user identifier in a single training, validation, or test group.
  \item[Validation partition] The employee groups used to compare
        model candidates and choose the review capacity.
  \item[Test partition] The held-out employee groups used for the
        final reported estimate after model and capacity selection.
  \item[Average Precision] A summary of the precision-recall ranking
        curve, used here to compare models over score cutoffs.
  \item[Review capacity] The chosen fraction of ranked records that can
        be presented for inspection in a fixed-size queue.
  \item[Percentile rank] A record's relative position among the scores
        in the currently analyzed dataset; it is not a probability.
  \item[Consensus score] The mean of four model percentile ranks for
        an employee-day. The dashboard ranks each employee using the
        highest daily consensus score.
  \item[Model agreement] The number of model-specific employee rankings
        that fall in each model's top ten percent under the dashboard
        rule.
  \item[False positive in this report] A selected employee-day without
        a matching known-window label. Because labels are incomplete,
        this term does not establish benign activity.
  \item[Model bundle] The local joblib artifact containing estimator
        objects, model names, and the ordered feature-column list used
        by the dashboard.
\end{description}

\section{Detailed Data Preparation Method}
\subsection{Input validation and parsing}
The dashboard accepts five source files with fixed filenames. It first
checks that each file exists and then checks that the normalized header
contains the two fields required for aggregation: a timestamp and a user
identifier. Optional activity and attachment fields add source-specific
features when present. A missing optional field therefore removes that
particular feature contribution, while a missing required field prevents
the source from being processed. This distinction is important when
reviewing files exported from different schemas.

The parser reads up to 25,000 records at a time. Timestamps are parsed
with invalid values coerced to missing, user identifiers are converted
to strings and trimmed, and rows with unusable identifiers or dates are
discarded. Duplicate removal is applied within each chunk. Because a
duplicate may occur in two different chunks, the saved quality summary
does not establish globally unique source rows. An operational data
quality report should therefore include cross-chunk duplicate checks
when exact event counts matter.

\subsection{Aggregation semantics}
Each retained source row contributes one event to the relevant
employee-day count. The timestamp is converted to a calendar day, and
the hour is classified as after-hours if it is earlier than 06:00 or at
or later than 18:00. Device rows additionally contribute to the
connection feature when their activity value equals ``connect'' after
lowercasing. Email rows contribute the numeric attachment field when it
can be parsed; invalid attachment values contribute zero. The feature
tables from all sources are aligned by user and day, and missing values
are filled with zero before model scoring.

This representation deliberately reduces millions of event rows to a
small number of counts. It discards within-day ordering, exact event
times after the after-hours indicator is calculated, and the semantic
content of events. It is therefore suitable for a compact demonstration
of ranking but cannot reproduce the complete event narrative needed for
an investigation.

\subsection{Label construction and uncertainty}
Training labels are created by matching user identifiers to the
answer-file incident windows for release 4.2. The start and end are
normalized to days and the interval includes both boundary dates. A
positive employee-day means that at least one known window covers that
user and day. This rule is deterministic and easy to reproduce, but it
does not identify which event within the day was relevant. It also
cannot guarantee that days outside the published windows are truly
negative. For that reason, this report uses ``unmatched'' when
describing model false positives and treats the target as a known-window
indicator rather than a complete ground truth.

\section{Model and Evaluation Details}
\subsection{Preprocessing and score direction}
The Logistic Regression pipeline imputes missing numeric values with
the median and standardizes features before fitting. Class weighting
increases the contribution of the rare positive examples during its
optimization. The Decision Tree and Random Forest consume numeric
counts directly and use balanced class weights to account for the
unequal label frequencies. The Random Forest averages predictions over
200 trees; the tree depth and minimum leaf settings regularize the
individual decision rules. Isolation Forest is fitted without labels,
and its decision function is negated so that a larger score consistently
means a higher rank across the application.

Raw scores from the four estimators have different meanings and scales.
In the dashboard, each model's scores are converted to percentile ranks
within the currently selected dataset. The ranks can be averaged for a
consensus view, but they are not calibrated probabilities and are not
comparable across separate folder analyses. Adding or removing records
can change percentile values even when a particular employee-day's raw
model score does not change.

\subsection{Employee-grouped partitioning}
All days belonging to a synthetic employee are assigned to the same
partition. The first split reserves test employees; a second grouped
split separates training and validation employees from the remaining
groups. The result contains 198,259 training rows, 66,075 validation
rows, and 66,118 test rows. The respective known-positive counts are
815, 260, and 289. No employee identifier is shared between these
partitions. The grouping addresses repeated-person leakage, but it does
not simulate future deployment in time: dates from the same broad
dataset period may appear across partitions for different employees.

\subsection{Candidate augmentation}
The augmentation candidate creates one perturbed example for each
positive training employee-day. Event counts are resampled with
count-aware Poisson and binomial operations intended to preserve
nonnegative integer-like behavior. Only training rows are augmented;
validation and test records remain unchanged. The candidate is kept
only when its validation Average Precision exceeds that of the
real-data Random Forest. This comparison provides evidence that the
candidate improved ranking on this validation split, but it does not
prove that synthetic examples represent real incident behavior or that
the gain will persist on another dataset.

\subsection{Capacity-based decision rule}
The workflow evaluates several review rates and selects the rate with
the best validation F1 for the selected model. At evaluation time the
top-scored records are selected anew within each partition, so the
operating point represents a queue-size assumption. At a one-percent
capacity, the held-out test queue contains 662 of 66,118 employee-days;
at five percent it contains 3,306. The first setting is more selective,
while the larger queue retrieves a greater fraction of known positive
days. Neither rate is a score threshold that can be carried to another
population without recalibration and review of capacity constraints.

\section{Detailed Dashboard and API Workflow}
\subsection{Request lifecycle}
The local React client starts an analysis request after the analyst
selects the required folder. In the upload flow, the API accepts the
expected filenames, rejects duplicate or missing required files, writes
the accepted files to a temporary directory, and closes the uploaded
file handles when processing finishes. The analysis lock serializes
requests because the service keeps the latest employee-day table and
ranking in process memory for detail requests. The API returns the
employee report and a summary containing the employee count, flagged
count, review count, and number of active dates.

The progress endpoint exposes a percentage and stage message. Progress
is reported at source and model milestones; it is not based on a
measurement of remaining rows or compute time. A client-side remaining
time estimate is consequently an extrapolation from elapsed time and
reported progress. The final milestone indicates successful completion
of scoring and report creation, while an exception resets the progress
state and returns an error response.

\subsection{Employee detail and displayed signals}
The employee detail request selects one employee from the most recent
in-memory report and returns that employee's relative model ranks,
agreement count, active-day count, review status, and daily activity
table. The explanation string is generated from a small set of
aggregated signal rules on that employee's highest-consensus day. It
may mention after-hours logons, device connections, file activity,
email, or web event counts when the count meets a dataset-level
percentile condition. These rules describe measurable features; they do
not explain why an event occurred or establish a policy violation.

The API writes two CSV outputs after each successful run. These files
are convenient for inspection, but they are not a durable case system:
there is no transaction history, analyst annotation, authorization
record, or deletion schedule. A later run can replace prior outputs.
The current service also retains the latest data frames in process
memory until replaced or the process exits. Both behaviors should be
considered when evaluating deployment controls.

\section{Risk, Privacy, and Operational Considerations}
\subsection{Data minimization}
The feature pipeline does not read message bodies, web destinations,
file contents, or filenames. It does process user identifiers, exact
timestamps during parsing, source event types, and aggregate counts.
This reduces the semantic content processed but does not make the data
anonymous: an identifier linked to an employee can remain sensitive.
For the demonstration, the most appropriate handling is to use the
synthetic dataset, restrict local file access, and avoid copying raw
records or outputs into shared locations.

\subsection{Human review and evidentiary limits}
A ranked record should be treated as a prompt to inspect authorized
source material. Review should consider the employee's role, assigned
schedule, approved exceptions, business calendar, and relevant system
context. Analysts should record the basis for a decision and seek
independent corroboration before escalating a lead. The tool does not
provide a mechanism to capture those notes, challenge inaccurate source
data, or record an employment decision; those activities must remain
outside the prototype and follow institutional policy.

\subsection{Potential sources of error}
The fixed after-hours window can label approved shift work as unusual.
Aggregate volumes can reflect differences in role, workload, tenure, or
system access. Sparse incident labels may mark ordinary events on an
incident day as positive and may leave other relevant days unlabelled.
Duplicate rows across chunks can inflate counts, while malformed data
can remove activity from a user's profile. A new folder with a
different event distribution also changes percentile ranks and can
alter employee ordering. These mechanisms can generate both missed
leads and unnecessary review.

\subsection{Controls needed before operational use}
A deployment would need an explicit lawful purpose and authorization,
named data owners, least-privilege access, secure transfer and storage,
auditable model and data versions, retention and deletion rules, and a
documented process for correcting source data. Model validation should
cover relevant employee groups, time periods, and operating conditions.
Review burden and disparate impact should be measured with appropriate
stakeholders. Analysts should be trained to distinguish rank from
probability and known-window labels from verified ground truth. The
current repository does not implement these controls, so the dashboard
is limited to controlled demonstration use.

\section{Reproducibility and Review Protocol}
\subsection{Reproducing the saved experiment}
To reproduce the analysis, use the same CERT r4.2 activity files and
answer file, run the notebook cells in order, and preserve the recorded
split and estimator configuration. Verify that the generated aggregate
schema contains the expected feature columns and that all positive
labels lie within employee groups assigned to exactly one partition.
Run model evaluation after the split is fixed, compare validation
Average Precision for the real and augmented Random Forest candidates,
then calculate test metrics using the selected model and queue rate.
The model bundle should be generated only after the evaluation path has
completed and should be checked for the four expected model names and
ordered feature list before it is used by the dashboard.

\subsection{Reviewing an individual result}
An analyst using the demonstration should first confirm that the
selected folder belongs to an authorized, synthetic or otherwise
approved exercise. After processing, the analyst can use the employee
directory to identify a relative review priority, inspect the four
model ranks and their agreement, and open the highest-ranked activity
days. Each displayed count should be interpreted in context and checked
against original records. The analyst should not infer intent from an
after-hours count, attachment count, or model rank alone. Because the
application lacks case notes, any independent review record should be
kept in an approved system with access controls and retention rules.
